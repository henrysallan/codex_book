Codex MCP + Candidate Edits — Spec

Status: proposal, awaiting answers to §12. Written 2026-08-21 after reading the current tool loop (src/lib/ai/tools.ts, chat/route.ts, router.ts), the editor save path, the store, and the auth layer.

0. In one paragraph

Expose Codex to external Claude clients (claude.ai, Claude Desktop, Claude Code) through a remote MCP server hosted inside the Next.js app at /api/mcp. It shares one tool registry with the in-app chat loop. Reads are direct. Writes are never direct: Claude can only create proposals — a first-class note_proposals row that the paired browser renders as green (added) / blue (removed) marks over a read-only preview, with an Accept / Reject bar. Only a human click applies the change, through the same expectedUpdatedAt-guarded save the editor already uses. A server-side intent gate refuses proposal calls whose quoted user instruction reads as a question rather than an explicit edit request. One browser per user is the “surface” Claude drives; it’s chosen through a pairing-code handshake in Settings → Connect to Claude.

1. Goals and non-goals

Goals

  • Claude (outside the app) can find, read, and reason over notes with the same isolation guarantees as the in-app chat (runAsUser, scoped service-role queries).
  • Claude can drive the UI of exactly one paired browser: know what’s open / selected, open a note.
  • Claude can propose edits and new notes. Proposals are visible, diffed, reviewable, and inert until accepted.
  • Proposing is hard to trigger by accident. Questions and feedback about text do not become edits.
  • The in-app chat panel gets the same capability (proposals instead of silent create_note).

Non-goals (for this spec)

  • Raw SQL from Claude. Typed tools only; see §11 for an optional, locked-down read-only variant later.
  • Deleting notes, moving folders, or bulk operations from Claude.
  • Live collaborative editing / CRDT. We keep whole-column saves with stale-write detection.
  • Editing moodboards, database blocks, or PDFs. Proposals cover prose notes (note, daily, quick notes).

2. What exists, and what to keep / change

The current loop works and the isolation layer is good. But as the base for an MCP surface it has specific problems worth fixing rather than duplicating.

Keep

  • getToolDb() — service-role client that forces user_id on every select and p_user_id on every RPC. This is the actual tenant boundary; the MCP route uses it unchanged.
  • runAsUser() / uid() (AsyncLocalStorage, fails closed). Wrap every MCP tool call in it.
  • createFolderPathResolver, folder-path resolution in create_note, markdownToBlockNote, blocksToPlainText.
  • serverAuth.getUserFromRequest — validates a Supabase JWT. The MCP route reuses it for OAuth and bearer tokens alike.
  • Editor’s expectedUpdatedAt → StaleWriteError → applyRemoteDocument reseed path. Accepting a proposal is “a save from elsewhere”, and the editor already knows how to absorb one.

4. Auth and pairing (“Connect to Claude”)

Two layers, deliberately separate: identity (which account) and surface (which browser window).

4.1 Identity

A — Supabase OAuth 2.1 Server (recommended; needed for claude.ai / Desktop). Supabase Auth can act as the OAuth 2.1 authorization server for MCP clients — GA, with dynamic client registration and PKCE. Codex already uses Supabase Auth, so:

  1. Enable the OAuth server in the Supabase dashboard.
  2. Serve RFC 9728 metadata at /.well-known/oauth-protected-resource pointing at the project’s authorization server. Clients discover it from a 401 + WWW-Authenticate on /api/mcp.
  3. The client runs DCR + PKCE against Supabase; the user logs in with Google as today.
  4. The access token is a normal Supabase JWT → getUserFromRequest() validates it unchanged.

Consent UI can be hosted in our app (Supabase supports a custom authorize page) — that’s where the pairing code (§4.2) can also be shown. Verify the exact issuer path and custom-page mechanics against the Supabase docs at implementation time.

B — Personal access token (day one; Claude Code and scripts). Settings → Connect to Claude → “Create token” → cdx_… shown once, stored as a SHA-256 hash in mcp_tokens. Used as Authorization: Bearer cdx_…:

claude mcp add --transport http codex https://<app>/api/mcp --header "Authorization: Bearer cdx_…"

claude.ai’s connector UI has no header field, so B alone doesn’t reach claude.ai/Desktop.

4.2 Surface pairing — “make sure the codes match”

OAuth proves the account. Pairing picks the one browser window Claude may drive and adds the visible human step you described.

  1. Claude calls connect_to_codex() (or any workspace tool while unpaired). Server creates pairing_requests { code: "7K3-QPD", client_label, expires_at: +5 min } and returns the code. Claude tells the user: “Pairing code 7K3-QPD — confirm it in Codex → Settings → Connect to Claude.” The tool long-polls up to 55 s for the outcome.
  2. The browser’s Settings panel (subscribed to the surface channel while open) shows: Claude (claude.ai) wants to connect · 7K3-QPD · [The codes match — connect] [Deny]
  3. Confirm → upsert claude_links { user_id PK, surface_id, surface_label }. The PK enforces one browser per user. Any other tab with a different surface_id receives link_changed and shows “Another window is connected to Claude · [Take over]”.
  4. connect_to_codex resolves paired. Workspace tools now work.
  • surface_id lives in localStorage; pairing survives reloads. Re-pair only when switching browsers.
  • Heartbeat every 15 s; last_seen_at older than 45 s ⇒ offline. Workspace tools then return { ok:false, code:'surface_offline', message:'Codex isn't open in the paired window. Ask the user to open Codex, or to re-pair from Settings.' }.
  • Settings shows: paired window label, last seen, Disconnect, token list with revoke.

5. The surface channel (browser ↔︎ server)

There is no realtime channel in the app today. The MCP route runs in a stateless function, so the channel must not require the server to hold a socket.

  • Server → browser: Supabase Realtime private broadcast channel surface:{userId} (config: { private: true } + an RLS policy on realtime.messages so only auth.uid() = userId can join). The server publishes over REST with the service role — no persistent connection. Messages: open_note {documentId, blockId?}, flush_save, proposal_created {proposalId, documentId}, proposal_withdrawn, document_updated {documentId, updatedAt}, pairing_request {code, clientLabel}, link_changed {surfaceId}.

  • Browser → server: no broadcast. The browser writes claude_links.state (anon key, RLS) on change, debounced 300 ms, plus heartbeat. Server “awaits an ack” by polling that row (250 ms, ≤ 3 s). Keeps the server stateless and the protocol trivially debuggable.

  • State mirror shape:

    { activeDocumentId: string|null, activeTitle: string|null,
  view: 'dashboard'|'document'|'graph',
  openTabs: {id:string,title:string}[],
  selection: { docId:string, text:string, blockIds:string[] } | null,
  isDirty: boolean,            // editor has an unsaved 1s-debounce pending
  pendingProposalIds: string[] }

  • “In my current note” → read_note({ current: true }) → state.activeDocumentId; if isDirty, send flush_save, wait for isDirty=false (≤ 2 s), then read from Postgres. Selection text comes straight from the mirror.

  • Fallback if Realtime is undesirable: an mcp_commands table the paired browser polls every 2 s. Same message shapes; swap the transport, not the protocol.

7. Candidate edits (proposals)

7.1 Principles

  1. Nothing Claude does mutates a note. A proposal is inert data. Only POST /api/proposals/:id/accept from the paired browser writes to documents.
  2. The preview never touches autosave. Review renders into a second, read-only editor; the live editor is unmounted while reviewing so the 1 s debounce cannot fire on preview content.
  3. Ops are anchored, not positional. Every op targets a block id and carries the hash of that block as Claude saw it, so a proposal can still apply (or fail honestly) after the user keeps typing.
  4. Claude can’t quietly replace a whole note. rewrite_all exists but is refused for notes that contain blocks markdown can’t round-trip.

7.2 Data model

create table note_proposals (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,

  instruction_quote text not null,

  -- create
  title text, folder_id uuid references folders(id), tags text[],
  -- edit

  base_updated_at timestamptz,
  base_content_hash text,
  base_content jsonb,                  -- snapshot for "Undo" after accept
  result_blocks jsonb,                 -- full doc if every op is accepted

7.3 Op language and anchors

read_note (format anchored) gives Claude stable handles. Anchors are the shortest unique prefix of the BlockNote block id (6 chars by default):

⟦a1f2c9⟧ # Reading: Weil, Gravity and Grace
⟦b7e210⟧ First pass through the notebooks. Three themes keep recurring…
⟦c03d44⟧ ## Attention
⟦d9a8f1⟧ - Attention as the rarest form of generosity
⟦e4b6c2⟧   - (child) cf. ⟦pageLink: Simone Weil — biography⟧
⟦f51e07⟧ [database block "Quotes" · 3 columns × 12 rows — not editable with markdown]

Ops (server assigns id, resolves anchor → blockId, records baseHash):

Op Fields Semantics
replace_text anchor, find, replace Inline. find must occur exactly once in the block’s plain text. Untouched runs keep their styles. Preferred for small edits.
replace_block anchor, markdown Whole block. Children preserved.
insert_after anchor \| "start", markdown One or more blocks.
delete_block anchor Block and children.
append markdown At the end of the note.
rewrite_all markdown Whole note. Refused if the note contains database, image/file, column, or pageLink-bearing blocks — the error lists their anchors and tells Claude to use targeted ops.

Markdown → blocks via the existing markdownToBlockNote (extend it to turn [[Title]] into a pageLink when a title matches). Blocks → anchored markdown via the currently-unused blocksToMarkdown.ts, resurrected, with non-convertible blocks rendered as bracketed descriptions.

7.4 Server pipeline (propose_edit)

  1. Resolve target (current → surface state; flush if dirty). Must be owned, doc_type ∈ {note, daily, quick note}, no database-only docs.
  2. Gate (§8). Refuse with a structured, actionable error if it fails.
  3. Resolve anchors against the current content; reject unknown/ambiguous anchors, find strings that match ≠ 1 time, ops over database/column blocks.
  4. Compute result_blocks (apply all ops) and preview_blocks (§7.5) and hunks[].
  5. Supersede any pending proposal on the same note (status superseded); refuse if one was created < 30 s ago by the same source (spam brake).
  6. Insert row, broadcast proposal_created, return.

  • Marks. Inline word-level diff (diffWords) inside changed text blocks: inserted runs carry a custom BlockNote style suggestion: "insert" (green tint, e.g. #dcfce7 / text #166534), removed runs suggestion: "delete" (blue tint #dbeafe, text #1e40af, strikethrough). Whole-block add/remove (and non-text blocks) get a block-level decoration: 3 px left rule + faint tint in the same hue. Implemented with createReactStyleSpec for inline and a small ProseMirror decoration plugin keyed by block id for block-level.
  • Preview editor. A second useCreateBlockNote instance, editable={false}, same schema + the suggestion style, seeded with preview_blocks. The live editor is unmounted.
  • Bar actions. Accept all → §7.6. Reject → status rejected, back to the live editor. Show original toggles marks off. Dismiss for now (overflow menu) hides the preview but keeps the proposal pending and the badge lit. ⌘⏎ accepts; there is no keyboard reject.
  • Per-hunk (P2): a stepper in the bar (1/3 ‹ ›, ✓ / ✗ per hunk). Accepting a subset recomputes the result from accepted ops only.
  • Not the open note. Toast “Claude proposed changes to Weil notes · [Review]”; a green dot on the sidebar item and tab. A small Proposals inbox (count badge) in the chat panel header lists all pending ones.
  • New notes (kind='create'). A ghost entry (dashed outline, “Proposed”) in the target folder; opening it shows the full body as an insertion with the same bar. Accept creates the document via the normal insert path; Reject removes the ghost.

7.6 Accept pipeline

POST /api/proposals/:id/accept { hunkIds? } — bearer-authed, service role, runAsUser:

  1. Load proposal + current document. If status ≠ pending → 409.
  2. If documents.updated_at == base_updated_at → use result_blocks (or recompute from the accepted subset).
  3. Else rebase: for each accepted op, locate the block by id in the current content; if its hash equals baseHash, apply; if missing or changed → conflict. Any conflict → 409 { stale: true, conflicts: [hunkIds] }; the bar shows “The note changed since this was proposed — 1 of 3 changes can’t apply · [Apply the rest] [Reject]”. Proposal status → stale until resolved.
  4. updateDocument(id, { content }, { expectedUpdatedAt }) (server-side, same function the editor uses). On StaleWriteError, retry the rebase once, then 409.
  5. Server-side syncBacklinks (today it’s client-only; add the server helper), then fire-and-forget indexDocument.
  6. Mark accepted, set applied_updated_at, broadcast document_updated.
  7. Browser: store updates activeDocument; the existing applyRemoteDocument reseeds the live editor; review mode closes; toast “Applied 3 changes · Undo” (30 s; Undo writes base_content back with the same guard).

Reject: status='rejected', resolved_at, broadcast. No document write.

7.7 What Claude sees

  • propose_* returns immediately with proposalId. The description instructs: say you’ve proposed the change and where to review it; never say the note was updated.
  • await_review lets Claude block (≤ 55 s) when the user is clearly at the keyboard.
  • On rejected, Claude can ask what to change. On stale, get_proposal returns fresh anchors for the touched blocks so a re-propose is one cheap call, not a re-read.

8. The intent gate

We don’t control the client model’s reasoning, so the guard has to live server-side and be independent of prompt obedience. Defense in depth:

  1. Policy text, once. MCP server instructions + both propose_* descriptions: Only propose when the user explicitly asked for the note to be changed. Questions, critiques, “what would you change”, “is this too long” → answer in chat. If unsure, ask “Want me to propose that as an edit to ‹title›?” and only then call with their reply as confirmation_quote.
  2. Required evidence. instruction_quote — the user’s words, verbatim — is a required input. Optional confirmation_quote for the ask-then-confirm path.
  3. Classifier classifyEditIntent(instruction, confirmation?) → explicit | implicit | question | unclear:
    • Fast path (regex, no API): imperative edit verb (update, edit, change, rewrite, add, insert, append, remove, delete, fix, replace, put, tighten, expand, shorten, reorganize) aimed at a note/section/paragraph/“this”/“it”/“my …” ⇒ explicit. Interrogatives (?, what/how/should/ is this/do you think/would you) with no imperative ⇒ question.
    • Otherwise Groq 8B through groqLimited() (or Haiku) with a tight few-shot rubric, temperature 0, one token out.
    • Passes only on explicit, or implicit with an affirmative confirmation_quote.
  4. Refusal is actionable. { ok:false, code:'needs_explicit_request', message:'The quoted message reads as a question or feedback, not a request to change the note. Answer it in chat. If they want the change, ask "Want me to propose that edit to ‹title›?" and call again with their reply as confirmation_quote.' }
  5. Brakes. ≤ 1 pending proposal per note (new supersedes), ≤ 50 ops, ≤ 20k chars of markdown, 30 s spam window. Every verdict logged (proposal_gate_logs) for tuning. Settings toggle Strict mode: always require confirmation_quote.
User said Verdict Result
“Is the intro too long?” question answer in chat
“The intro is too long.” implicit blocked → Claude asks; “yes” unlocks
“Tighten the intro.” explicit proposal
“Could you tighten the intro?” explicit (polite imperative) proposal
“What would you change about this?” question answer in chat
“Add a section on attention to my Weil note.” explicit proposal
“yes, do it” (after “want me to propose…”) confirmation proposal

And after all of that, the Accept button is the real safety. The gate is about noise, not safety — even a gate miss produces only an inert preview.

9. In-app chat parity

  • The chat loop consumes the same registry. It gains propose_edit / propose_new_note; create_note is removed (or kept behind an opt-in “trusted chat” setting — your call, §12).
  • instruction_quote for the chat surface is verified server-side against the actual last user message (the server has it), so the chat path can’t be talked into a forged quote.
  • SSE gains a generic tool_event; ChatPanel renders a proposal card (“Proposed 3 changes to Weil notes · Review”) and the editor enters review mode through the same store path.
  • The BASE_SYSTEM prompt gets the policy paragraph from §8.1. The TIER0 regexes (“fix / improve / edit this”) stop being retrieval-only hints: with a note open and the gate passed, Claude proposes.

10. Phasing

P0 — Foundations (≈ 2–3 days). Registry refactor (zod, consolidated read tools, chat loop switched over). /api/mcp via mcp-handler with PAT auth. Settings → Connect to Claude (token create/revoke, pairing confirmation). claude_links + heartbeat + state mirror + Realtime private channel. Read + workspace tools. Exit: from Claude Code, “what note do I have open?” and “open my note on Weil” work against the paired window.

P1 — Candidate edits (≈ 4–5 days). note_proposals, op language, anchored read_note, diff/preview engine, suggestion styles + block decorations, intent gate, propose_* tools, ProposalBar + preview editor (accept all / reject), accept pipeline with rebase/stale, toasts and badges, chat parity. Exit: “add a summary section to my current note” → green preview → Accept → saved, backlinked, indexed. “Is this intro too long?” never produces a proposal.

P2 — Reach and polish (≈ 3 days). Supabase OAuth 2.1 server for claude.ai / Desktop. Per-hunk accept. Ghost notes + Proposals inbox. Metadata proposals (title / tags / folder). Undo after accept. Expiry job.

P3 — Optional. Read-only SQL tool under a dedicated Postgres role (SELECT only, user-scoped views, statement_timeout), off by default. Annotation tools. Database-block row ops.

11. Risks and sharp edges

  • Markdown round-trip fidelity. pageLink inlines, multi-column, database blocks, images. The op language sidesteps most of it (untouched blocks are copied byte-for-byte), rewrite_all is refused for those notes, and replace_text splits inline runs rather than re-serializing them.
  • Autosave during review. Must be structurally impossible, not just guarded: the live editor is unmounted, the preview editor has no onChange.
  • Staleness. Users keep typing after Claude proposes. Block-id anchors + base hashes make rebase cheap and conflicts explicit. Never silently overwrite.
  • Channel security. Broadcast channels are public by default; the surface channel must be private with an RLS policy on realtime.messages, or anyone with the anon key who guesses a user id could push open_note commands.
  • Client timeouts. MCP clients time out long tool calls; cap long-polls at 55 s and set maxDuration = 60.
  • Tool schema weight. 16 tools with terse descriptions. Resist re-growing to 27.
  • Consent UX for OAuth. If Supabase’s hosted consent page can’t show the pairing code, pairing stays a separate step (it works either way; it’s just one more click).
  • Elicitation (server asks the user mid-call) is Claude Code-only today. Don’t depend on it; the review bar is the confirmation surface everywhere.
